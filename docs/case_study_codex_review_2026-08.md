# Case Study:用另一個 agent(codex)做 code review,一次抓到 6 個問題

> 這份文件記錄 2026-08-04 的一次事後 code review：Spencer 拿最近兩個已 push 的
> commit(`ef03363`、`0cba8d7`)請 codex 單獨審查，抓到 6 個問題（3 高 + 3 中）。
> 全部由 Claude 逐一在程式碼中重現確認、修正、補上回歸測試，1047 tests green。
> 這 6 個問題全部不是「明顯的語法錯誤」，而是「邏輯上看起來合理、但跟系統其他
> 部分的假設兜不起來」的類型——這正是同一個 agent 很難自己抓到的錯誤形狀。

## 為什麼會抓不到:同一個 agent 審查自己寫的 code 的結構性盲點

這 6 個問題有一個共通點：**每一個都是「寫下這段程式碼的當下，邏輯是自洽的」**。
例如：

- Digest 送出後關閉 pending rows，這行程式碼本身沒有 bug——寫的人當下想的是
  「已經讓主人看過了，該關閉」，只是沒有回頭檢查 digest 文字本身**其實沒有真的
  附上內容**，兩個決定分別做的時候都合理，合起來才是漏洞。
- `has_pet`/`wants_bbq` 只在 `True` 時寫回 state，是為了不讓「沒提到寵物的訊息」
  誤清空既有旗標——這個防呆本身是對的，只是連帶把「明確說沒有寵物」也一起擋掉了，
  因為當時的資料型別（bare bool）沒有能力表達「沒提到」跟「明確說沒有」的差異。
- 同名客人選號重新查詢排序，是為了讓清單「即時反映最新狀況」——這個出發點也沒錯，
  只是沒想到主人的回覆跟顯示清單之間存在時間差。

同一個寫這段程式的 agent，在原本的 context 裡會傾向於「順著自己剛剛做的設計決策
去驗證」，而不會回頭問「這個決策跟系統其他地方的假設矛盾嗎」。這不是能力問題，是
**視角問題**——自己審查自己的推理鏈，很難跳出那條推理鏈本身去質疑前提。

## 另一個 agent 帶來的東西：沒有「上一步決策」的包袱

codex 在做這次 review 時，沒有參與過這些 commit 的實作過程，看到的只有最終的
程式碼跟它彼此之間的關係，所以它問的問題是「這段程式碼跟那段程式碼的假設一致
嗎」，而不是「這段程式碼有沒有照我原本的設計做」。這 6 個問題全部是這種
**跨檔案 / 跨層邏輯不一致**：

| # | 不一致發生在哪兩處之間 |
|---|---|
| 1 | digest 推播的**文字內容**（只給數量）vs. digest 推播後的**副作用**（關閉全部訊息） |
| 2 | `pricing_policy.py` 的**程式行為**（自動加價）vs. `config.json` / `pricing_rules.md` 的**文件承諾**（不自動加價） |
| 3 | `log_payload_to_state_slots.py` 的**防呆意圖**（不讓沉默清空旗標）vs. **實際資料型別**（bool 表達不出「沉默」跟「否定」的差異） |
| 4 | 否定詞清單（`不用`/`不需要`/`沒有`/`無`）vs. 口語常見的「不要」不在清單內 |
| 5 | label-theft 偷取防呆的**字串比對**（要求緊鄰）vs. 使用者輸入的**真實排版**（label 跟數字間常有空格） |
| 6 | 候選清單顯示當下的**排序快照**（隱含假設：查完就馬上選）vs. 主人真實的**操作節奏**（看到清單後可能過一陣子才回） |

這種「A 處的假設跟 B 處的假設對不上」的問題，全部要跨檔案理解全貌才看得出來，
單一函式內部的 code review（或原作者自己重讀一次）很容易漏掉，因為兩邊分開看
都「看起來對」。

## 過程

1. Spencer 請 codex 對 `ef03363`、`0cba8d7` 兩個 commit 做獨立 review，拿到 6 項
   結構化報告（含檔案:行號、現象、可重現的探測結果）。
2. Claude 對每一項**先重現再修正**：讀原始碼確認問題成立、寫最小重現腳本驗證
   （而非直接相信報告文字），第 2 項（BBQ 加價機制）因為牽涉護城河報價邏輯，
   先用 `AskUserQuestion` 跟 Spencer 確認要「比照寵物費機制」還是「維持不自動
   加價」，第 6 項（同名選號）也先確認要做到「輕量修」還是「完整快照重構」，
   才動手。
3. 修正過程中又多抓到 2 個同類型但 codex 沒報告的漏洞（`pet_parser.py` 的
   「不要寵物」跟第 5 項修正時同一份邏輯造成的迴歸——`_TRAILING_NUMBER` 沒有
   容忍空白，導致把「10 大人 2 小孩」這種正常斷句誤判成偷取），都補上了回歸
   測試後再繼續。
4. 全部 6 項改完後跑完整 pytest：**1047 tests green**（原 1035 + 本次新增的
   regression tests）。

## 具體修法摘要

- **#1 digest 內容消失**：`_check_and_send_digest_for_tenant` 不再在推播成功後
  立刻關閉 pending rows——digest 本來就只送數量提示，真正的內容要等主人打
  `/待回覆` 才顯示，只有真正顯示內容的那個路徑才有資格關閉。
- **#2 BBQ 加價**：確認方向是「比照寵物費機制」（自動加總 + 標記需主人確認），
  `config.json` 的 `auto_add_fee_in_v1_5` 改 `true`，`pricing_rules.md` 同步。
  程式邏輯本身不用改，因為它一直以來的行為就是這樣。
- **#3 寵物/BBQ 改口清不掉舊狀態**：`PetParseResult`/`BbqParseResult` 新增
  `mentioned` 欄位，把 bool 升級成 tri-state（True 明確肯定 / False 明確否定 /
  None 沒提到），`inquiry_service.py` 轉譯，`log_payload_to_state_slots.py`
  遇到明確否定時才真的寫入 `False` 並把 `pet_count` 強制歸零。
- **#4「不要烤肉」誤判**：`bbq_parser.py`（以及順便修正的 `pet_parser.py`）否定
  詞清單補上「不要」。
- **#5 人數 parser 空格偷取**：`_has_label_theft` 的 label 比對、
  `_TRAILING_NUMBER` 的數字比對都補上 `\s*` 容忍空白間隔。
- **#6 同名選號**：`/<名字> <數字>` 這種形狀，先嘗試把整串（含結尾數字）當
  literal 顯示名稱精確查詢，查得到才用；查不到才照舊拆成「候選編號」解讀。
  候選清單排序仍可能因為時間差而漂移，維持為已知限制（機率極低，且屬於
  handoff/狀態機範圍，重構成本明顯高於效益）。

## 心得

這次的價值不在於抓到 bug 本身（bug 遲早會被真實客人踩到、回報），而在於
**用一個沒有「上一步決策」包袱的視角，去檢查現有程式碼跨檔案的邏輯一致性**。
這類問題的共通特徵是「兩邊分開看都合理，合起來才漏」，正是同一個 agent 在原本
的實作 context 裡最容易系統性忽略的地方。日後對護城河相關邏輯（報價、狀態機、
handoff）做較大改動後，適合比照這次流程：讓另一個沒參與實作的 agent 單獨
review，而不是只靠原作者自己重讀。
