# V1.5 Limitations

明確列出 V1.5 **不會做**的事,以及為什麼。

## 不會做的事

### 1. 不保證空房

即使接了 Google Calendar(V1.5 已接),系統也**不會主動告訴客人「這天有房」**。

Calendar 的角色是:
- 看到關鍵字標記 → 該晚被當「客滿」處理,系統不報價、轉人工
- 沒看到關鍵字標記 → 系統照常初步報價,但回覆中**不提空房狀態**,只附固定確認句

理由:民宿主可能漏標、用不同關鍵字、紙本記、剛接電話還沒記。系統說「沒看到標記」會被客人理解成「有房」,出事是民宿的責任。所以系統不主動講,只在「明確客滿」時擋住報價。

### 2. 不自動成立訂房

系統永遠不會替客人「鎖定」一個日期。所有最終確認由民宿人員執行。

### 3. 不收款、不收訂金

不串金流。30% 訂金、3,000 押金等政策只在文字中提及,實際收款由民宿人員處理。

### 4. LLM 只做模糊語意解析,不碰報價/狀態機/空房判斷

現況(已上線)已啟用 LLM(預設 DeepSeek V4 Flash,見 `docs/llm_model_selection.md`),
但僅用於「模糊語意解析」與「意圖判斷」,回傳結構化欄位給規則層使用。

理由:LLM 不可預測。詢價涉及金額、空房承諾,出錯成本太高,所以報價數字、狀態
轉換、空房判斷、客人可見文字一律留給規則層(見 CLAUDE.md「護城河」原則)。LLM
逾時 / 回傳壞 JSON 時,一律 fallback 到 rule-based 處理。

### 5. 主動回 FAQ 僅限白名單直答主題

WiFi、停車、包棟、設備/房型/位置、BBQ、訂金…等已列入 tier-1 白名單的主題
(`app/domain/faq_matcher.py`)會直接回覆固定文案。不在白名單內的問題,系統仍是
推播主人、不自動回,避免亂猜答案。

### 6. 不接 Messenger API

Messenger 用 Meta Business Suite 內建罐頭回覆撐著。V2 才補。

### 7. 白天不主動回覆(除非排程 On)

系統有 On/Off 開關,可手動 `/開機` `/關機`,也可設定自動時間排程(例如
23:00–08:00 自動 On)。這是為了避免系統跟主人在白天搶著回客人。詳見
`docs/operation_modes.md`。

### 8. 緊急訊息不回覆,只推播

偵測到「沒水、瓦斯、停電」這類關鍵字 → 立即推播主人,系統不自動回任何安撫訊息。

理由:緊急狀況不該由機器人講話。

## Fallback 行為

### Google Calendar API 連不上

不能假裝沒事繼續報價。改成:
- 不報價
- 回覆客人「需請民宿人員確認後再為您試算」
- 推播主人「Calendar 連不上,請檢查」

### LINE API 連不上

訊息留在資料庫、標記為「未送出」。主人 `/待回覆` 看得到。
