# Case Study:春節報價少一半,以及三個各自無害、疊起來致命的缺陷

> 2026-09-22/23 一筆真實客人對話暴露了三個彼此獨立的缺陷。單看每一個
> 都「只是小問題」,合起來讓系統對客人報出主人價格的一半,而回覆從頭到尾看起來
> 完全正常。

最後更新:2026-09-28

---

## 現場

客人 23:39 問:「明年 2/6-8(2晚)、6大4小、無寵物無烤肉、2台車、開3間房,
請問2晚費用?」

| | 金額 |
|---|---|
| 系統初步估算 | **NT$29,000**(週六房價 18,000 + 平日房價 12,000 − 連住折扣 1,000) |
| 主人 7:55 回覆 | **NT$60,000**(春節每晚 30,000 × 2,不打折) |

客人兩個數字都看到了。

同一段對話中間,客人回「1. 開 4/4/2,3間是多少錢? 2. 4間全開是多少?」,系統回了
一段「4/4 入住、4/5 退房,目前可能已有訂房」的莫名回覆。

---

## 根因一:房型組合記法被當成日期

客人在回答「要開幾間房」,列的是房型:4 人房、4 人房、2 人房。`date_parser` 的
`_DATE_PATTERN` 有前置 lookbehind `(?<![\d/])` 但沒有後置守衛,所以 `4/4/2` 的
前兩段照樣成立 → checkin=2026-04-04、checkout=None → `availability_probe` 假設
住一晚 → 拿 2026-04-04~04-05(**七個月前**)去查 Google Calendar → 行事曆上有
歷史訂房 → 「可能已有訂房」。

修法只有一條,而且是純語法的:day 群組後面加 `(?![ \t]*[/／])`。本模組不支援
年份,真實入住日永遠不會有第三段斜線。

**刻意不做語意判斷。** 我原本加了第二層「`開` 後面的日期一律當房型」,兩輪
Codex review 各打掉一個版本:

- 只看緊鄰的「開」→「有開 4/4 嗎?」的 `開` 是「有沒有營業」,日期正是問題本身,
  整個被丟掉。
- 加上 有/沒/還/營 前綴 + 後方 間/房 佐證 →「民宿開 4/4-4/6 的房間嗎?」沒有那些
  前綴,4/4 被跳過但 4/6 殘留成單獨入住日,系統會靜默去查 4/6-4/7 這個客人從沒
  提過的區間。

第二個比它要防的 bug 還糟(安靜地查錯區間 vs 多解析一個日期),所以整層拿掉。
剩下的缺口是兩房變體「開 4/4,2間」—— 那個形狀在生產與 eval 資料裡從未出現,
是我推理出來的,依 rule-of-three 不為它建機制。真要處理,正確的位置是對話狀態層
(`ConversationStateService._fill_contextual_room_count`),那裡知道系統剛問過
「要開幾間房?」,可以用真實狀態判斷而不是猜鄰近字元。

---

## 根因二:規則層完全不懂年份,而年份對是靠運氣

`date_parser` 只有一行 `year = reference_year or datetime.now().year`。全 repo
沒有任何 roll-over 或過去日期處理。實測(基準日 2026-09-23):

- `"明年 2/6-8"` → **2026**-02-06。「明年」完全被忽略。
- `"2/6-2/8"` → 2026-02-06,七個月前,照樣拿去報價與查行事曆。
- `"12/31入住 1/2退房"` → 2026-12-31 / 2026-01-02 → pricing 判 `invalid_date_range`
  → 客人收到「日期順序對不上」。**跨年訂單一律被擋。**

那這次為什麼畫面上是 2027?**純粹運氣。** 客人訊息裡有「2台車」,命中 parking
這個 FAQ topic → 觸發 `TYPE_3_FAQ_BOOKING_COLLISION` 把 LLM 叫起來 → LLM 順手把
「明年」解成 2027 → `_merge_dates`(LLM 日期優先)覆蓋掉規則層的 2026。

**客人如果沒提到車子,這筆就會用 2026-02-06 報價。** 年份是確定性推論,不該掛在
這條運氣路徑上 —— 這也違反護城河的精神。

修法:`parse_stay_dates` / `parse_inquiry` / `llm_fallback_parse` 新增
keyword-only 的 `reference_date`(只給 `reference_year` 則行為完全不變)。

三件事比預想的難:

1. **年份詞要逐日生效,不能整段共用。** Codex 連兩輪指向同一處:整段共用會把
   「今年12/31入住,明年1/2退房」—— 新年訂房極自然的寫法 —— 整筆推後一年,而這個
   case 在完全不加年份詞時本來就解得對。我第一次改成「衝突就退回 roll-forward」,
   Codex 指出那只是換一個 case 錯(「明年12/31入住,後年1/2退房」變成早一年)。
   最後改成每個日期取它前面最近的年份詞。
2. **區間要當一個整體解。** 逐日獨立 roll 在區間跨越今天時會爆掉:5/13 問
   「5/12 入住 5/14 退房」會把入住推到明年五月、退房留在今年 = 364 晚。改成
   「找出位移最小、且天數合理(≤31)的年份組合」,無解時退回字面同年讀法,讓真正
   打錯的「5/14 入住 5/12 退房」繼續走既有的反問。
3. **基準日要用訊息時間戳的租戶當地時間。** off-mode 訊息會在數小時後重播,用
   重播時間當基準會剛好在最容易跨年的日期上偏一年。而用 UTC 取 `.date()` 會在
   每天留下 8 小時的窗口讓基準日落後一天(台北 2027-01-01 01:00 收到「12/31 入住」
   會解成昨天)。

副作用:這讓測試不再隨真實時間腐化,也因此暴露 `tests/test_line_webhook.py` 的
fixture epoch 其實是 2023-11-14(斷言卻期待 2026),先前因為解析讀伺服器時鐘才
沒被發現。

還順手補了一道護城河強化:`_merge_dates` 原本讓 LLM 日期無條件優先,現在已經過去
的 LLM 日期一律不採用、退回規則層。只「拒絕」不「改寫」。

## 根因三:行事曆資料只有 2026,而查不到就當平常日

`config.json` 的 `special_dates` 手寫了 36 個 2026 國定假日 + 9 天春節,
**2027 那一批從來沒補上**。而 `pricing_policy._resolve_price_type` 對查不到的日期
一律當成平常日。

**這才是整件事最危險的地方:「沒有資料」與「沒有假日」在程式裡是同一件事。**
2027-02-06(六)→ 週六價 18,000、02-07(日)→ 平日價 12,000,回覆看起來毫無異常。

修法分兩半:

**推導(純函式,零 I/O)。** 政府辦公日曆表每一天都有 `isHoliday`,而且一般週六日
也是 `true`(description 為空),所以那個旗標本身不等於國定假日。規則:取
`isHoliday=true` 的日子切成連續區塊;區塊中有任一天具名 → 整個區塊算國定假日
(這正是連假前後那個週末拿到假日價的機制);具名日含 春節/除夕/小年夜 → 整個區塊
同時算春節;全區塊無名稱 → 只是個週末。

**這條規則從 2026 行事曆推導出的結果,與主人手打的 config 逐日完全一致**
(national 36/36、spring 9/9)。這條 golden 測試就是「改成自動抓取不會動到任何
2026 報價」的保證,也是這批改動不必人工重新驗一整年定價行為的依據。

**Gate(抓不到就不報價)。** 比照既有的 `availability_gate`,接在兩條報價路徑
呼叫 `calculate_price` 之前。行程觸及的年份只要有一年拿不到資料 → 不報價、回
既有的「請民宿人員為您進一步確認」、推播主人。

Codex 在這一段抓了最多問題,而且幾乎每一個都是「缺漏會靜默變成錯價」的變體:

- `bool(row.get("isHoliday"))` 強制轉型:缺欄位讀成「上班日」把連假從中切斷、
  字串 `"false"` 讀成假日。兩種情況該年都還是 365 筆,覆蓋率檢查完全不會發現。
- 重複日期:來源一天一列,重複一列會把連續區塊切成兩段。連假 2/27-3/1 若 2/28
  重複,3/1 會掉出假日清單、報平日價。
- config 不能宣稱涵蓋:租戶只為某年加一個自訂日期,原本會讓整年跳過抓取。我一開始
  用「先抓取、抓不到才退回 config」保住離線 2026,Codex 再指一次之後想清楚:那是在
  保護一個幾乎不存在的情境 —— 生產機本來就要連 LINE、OpenRouter、Google Calendar,
  完全斷網的話機器人根本沒法回覆。所以直接拿掉,涵蓋範圍只認快取。
- 跨年連假被年度切斷:`special_dates_for` 原本逐年各自推導,2028-12-30/31 在 2028
  自己的 payload 裡只是無名稱週末,整段被排除,跨年住宿那兩晚報週六/平日價。
- Gate 要求的年份必須含相鄰年度:一晚算不算假日取決於它所屬的整段連假,而連假會
  跨年。只要求「有計價夜」的年份會讓跨年住宿漏掉判斷依據。
- 失敗記憶必須會過期:我把 service 改成跨 request 共用(為了讓退避有效)之後,
  原本每 request 自然清空的失敗記憶變成永久有效 —— 一次暫時斷網就讓該年度的報價
  永遠轉人工到重啟。改成 5 分鐘 backoff。

---

## 第四件事:設定值本身也不對

三個根因修完,系統會報 28,000×2 − 1,000 = **55,000**,主人報 60,000。差的 5,000
不是 bug,是設定值:

- config 的春節價是 25,000 / 28,000 / 31,000(按房數),主人實際一律 30,000
- 主人報價沒扣連住折扣,系統無條件扣 (N−1)×1,000

改成:春節不分房數一律 30,000;行程中任一晚是春節或國定假日 → 整筆折扣歸零
(含假日的行程就是旺季行程)。週六價與暑假價不算旺季,照樣打折。

春節房價(2/7):NT$30,000

## 心得

**「系統該不該在此刻講話」之後,這次是「系統知不知道自己不知道」。**
前兩次的優先問題(23:00 排程打斷人工對話、FAQ 關鍵字劫持意圖)都是判斷不夠聰明。
這次不一樣:程式邏輯沒壞,壞的是**缺漏資料被當成有效資料**。查不到假日 → 當平常日;
沒寫年份 → 當今年。兩者都不會報錯、不會留 log、回覆看起來完全正常,只有金額是錯的。

所以這次加的不只是功能,而是一條原則:**寧可不報價,也不要靜默報錯價。**

**Codex 在這次的價值特別明顯。** 六個以上的 finding,幾乎每一個都是我作為實作者
跳不出自己推理鏈的那類:我加了一個機制,它指出這個機制讓某個本來正確的 case 變壞;
我修了一次,它指出修法只是換一個 case 錯;我把 service 改成共用,它指出這讓另一個
狀態變成永久有效。最有價值的一次是它讓我**把自己加的整層拿掉** —— 而我原本還把
錯誤的期望值寫進測試,等於把缺陷鎖進測試。

**rule-of-three 的界線也更清楚了。** 該建機制的是「真實出現過」的形狀
(`4/4/2`、`明年`、2027 缺資料);不該建的是推理出來的鄰居(`開 4/4,2間`、補班日
定價)。後者留註解說明為什麼不做,以及真要做時正確的位置在哪。
